# Supabase — schema proposal (NOT WIRED)

Status: **proposal**. Nothing here is implemented against a live Supabase
project. No credentials exist yet; the store seam ships with a local
implementation and the Supabase adapter is deliberately absent rather than
stubbed. Do not wire until the creds are in the host secret store.

Two jobs, deliberately kept apart:

1. **`mirror` — a read replica of the Sheets tables.** Enrichment currently
   reads Google Sheets directly and bumps the **300 requests/min** quota. The
   mirror moves those reads off Sheets.
2. **`app` — product storage** for user queries and sessions.

---

## The hard rule, and how it is enforced

> A stored user query is never evidence about a senator. Query/session data must
> have **no path** into `Promise Alignment - Matches`, `Decision Scores`, or
> anything the trust index reads.

Naming conventions do not enforce this — one careless join does the damage, and
it would look like a normal query in review. So the separation is enforced by
**Postgres privileges**, which fail closed:

| Role | `mirror` | `app` | Used by |
|---|---|---|---|
| `receipts_sync` | `SELECT, INSERT, UPDATE` | **no grant at all** | the Sheets→Postgres sync job |
| `receipts_app` | `SELECT` only | `SELECT, INSERT, UPDATE` | the Receipts server |
| `receipts_trust` | `SELECT` only | **`REVOKE ALL` — cannot even resolve the names** | the trust index / pipeline reads |

The load-bearing row is the last one. `receipts_trust` has no privilege on the
`app` schema whatsoever, so a query that tries to join user data into a trust
computation does not return wrong numbers — it **errors**. That is the
difference between a rule and a guarantee.

Two supporting constraints:

- **No foreign key ever points from `mirror` to `app`.** A FK is a path: it
  makes mirror rows referentially dependent on product data and gives a future
  `JOIN` an obvious-looking excuse. `app` references senators and actions **by
  value** (`text`), never by FK.
- **`mirror` is not authoritative.** Sheets remains the system of record until
  there is an explicit cutover decision. Every mirror row carries `synced_at`
  and `source_row_number` so a divergence is diagnosable rather than assumed.

### On naming

You asked for `app_*` / `mirror_*`. The proposal keeps those prefixes **and**
puts them in separate schemas — `app.app_queries`, `mirror.mirror_politicians`.
The redundancy is deliberate: the schema is what the grants attach to, and the
prefix means a bare table name in a log line or an error is still
self-identifying. Say the word if you want prefix-only.

## `mirror` — grounded in what the workflows actually read

Table list taken from the `googleSheets` read nodes in **WF10A, WF11, W7A and
W7B**, not from the specs:

| Sheets tab | Mirror table | Read by |
|---|---|---|
| Politicians | `mirror_politicians` | 5 nodes |
| Promise Alignment - Matches | `mirror_promise_alignment_matches` | 4 |
| Decision Scores | `mirror_decision_scores` | 3 |
| Platform Matches | `mirror_platform_matches` | 3 |
| Affected Stakeholders | `mirror_affected_stakeholders` | 1 |
| Impact Statements | `mirror_impact_statements` | 1 |
| Party Vote Positions | `mirror_party_vote_positions` | 1 |
| Donor Alignments | `mirror_donor_alignments` | 1 |
| Donors | `mirror_donors` | 1 |
| Politician Bill Actions | `mirror_politician_bill_actions` | 1 |
| Promise Matches | `mirror_promise_matches` | 1 |
| Roll Call Votes | `mirror_roll_call_votes` | 1 |
| Approved Taxonomy | `mirror_approved_taxonomy` | 1 |

⚠️ **`Promise Alignment - Matches` and `Decision Scores` are pipeline-WRITTEN**
as well as read (2 and 3 write nodes respectively). Mirroring them is fine;
writing to them from the app is not, and no role above can. The mirror copy is
strictly downstream.

⚠️ **`mirror_approved_taxonomy` must not become a second source of truth.**
`taxonomy.json` is generated by `tools/export-taxonomy.mjs` and is what the
query path reads. If the mirror ever fed retrieval, we would have two tables
that can disagree — the exact failure the exporter exists to prevent. Mirror it
for reporting only.

### Shape

Mirror tables are **wide and untyped-ish on purpose**: `jsonb` for the row body
plus typed columns only for what is indexed. Sheets columns move; a strict
schema turns a harmless upstream column addition into a sync outage.

```sql
create schema if not exists mirror;

create table mirror.mirror_promise_alignment_matches (
  id                bigserial primary key,
  match_uid         text not null,
  politician_id     text not null,
  promise_uid       text,
  bill_id           text,
  action_uid        text,
  row               jsonb not null,          -- the full Sheets row, verbatim
  source_row_number integer,                 -- provenance back to the tab
  synced_at         timestamptz not null default now(),
  unique (match_uid)
);
create index on mirror.mirror_promise_alignment_matches (politician_id);
create index on mirror.mirror_promise_alignment_matches (promise_uid);

comment on schema mirror is
  'Read replica of the Google Sheets pipeline tables. Sheets remains the system
   of record. Written only by receipts_sync. Never references the app schema.';
```

Every other mirror table follows the same pattern, keyed on its natural uid
(`politician_id`, `score_uid`, `vote_id`, …).

## `app` — queries and sessions

```sql
create schema if not exists app;

-- One row per query the user ran.
create table app.app_queries (
  id                  uuid primary key default gen_random_uuid(),
  session_id          uuid not null references app.app_sessions(id) on delete cascade,
  created_at          timestamptz not null default now(),

  -- What was asked. `politician_id` is TEXT, deliberately not a FK into
  -- mirror: a user's query must never be referentially entangled with the
  -- senator record it asked about.
  politician_id       text not null,

  -- THE TRAINING/ANALYSIS COLUMN. Captured deliberately: joined to the
  -- classification, the retrieved candidates and the verdict, this is the only
  -- dataset that can answer "what do people actually ask, and did we answer it
  -- well". It is the reason app_queries exists rather than being a log.
  --
  -- It sits BEHIND the corpus firewall. receipts_trust cannot read this column,
  -- because it cannot read this table, because it holds no privilege on this
  -- schema. Storing the text and keeping the firewall are orthogonal.
  promise_text        text not null,

  -- What the classifier made of it, and what the user corrected.
  classification      jsonb not null,        -- the Interpretation
  corrections_applied jsonb,                 -- CorrectionDelta[]
  statement_type      text not null,         -- 'Policy Position' | 'Campaign Promise'
  provenance          text not null,         -- 'default' | 'corpus' | 'asserted'

  -- ATTRIBUTION, persisted. When the Campaign Promise vocabulary came from the
  -- user asserting the premise, that fact must survive into any share or export
  -- read back out of this table. Dropping it converts their claim into ours.
  user_asserted_premise boolean not null default false,

  -- The frozen result, stored whole so a shared link renders exactly what the
  -- user saw rather than being recomputed against a moved record.
  result              jsonb,
  verdict             text,
  band                text,

  -- Operational, not evidentiary.
  models_used         jsonb,                 -- {classify, fulfill, explain}
  degraded            jsonb                  -- {relevance_applied, effect_source}
);

create table app.app_sessions (
  id          uuid primary key default gen_random_uuid(),
  created_at  timestamptz not null default now(),
  last_seen_at timestamptz not null default now(),
  user_agent  text,
  -- No raw IP. Store a salted hash if abuse controls ever need one.
  client_hash text
);

-- Demand capture, replacing the local append-only log in QueueStore.
create table app.app_senator_requests (
  id            uuid primary key default gen_random_uuid(),
  created_at    timestamptz not null default now(),
  politician_id text not null,
  promise_text  text,
  session_id    uuid references app.app_sessions(id) on delete set null
);

comment on schema app is
  'Product data: user queries, sessions, demand signals. NEVER an input to the
   trust index. receipts_trust holds no privilege here by design — a join from a
   trust query fails rather than silently returning user data as evidence.';
```

### Grants

```sql
revoke all on schema app   from public;
revoke all on schema mirror from public;

grant usage on schema mirror to receipts_sync, receipts_app, receipts_trust;
grant select, insert, update on all tables in schema mirror to receipts_sync;
grant select on all tables in schema mirror to receipts_app, receipts_trust;

grant usage on schema app to receipts_app;
grant select, insert, update on all tables in schema app to receipts_app;
-- receipts_trust and receipts_sync are granted NOTHING on app. Not read. Not usage.
```

RLS is enabled on all `app` tables with a service-role-only policy; the browser
never talks to Supabase directly, so there is no anon path.

## `promise_text` — three practical notes

Not objections; the decision is made. These are the things that bite later if
nobody writes them down now.

1. **The share-link read path returns it.** `getQuery(id)` hands back the whole
   stored query, `promise_text` included. Ids are v4 UUIDs, so they are not
   guessable — but if share links are ever made short or sequential, that
   changes. Keep them opaque.
2. **Users type incidental personal detail into free text.** "My senator voted
   against the bill that would have covered my daughter's insulin" is a normal
   thing to type. That lands in this column. It is fine to store, and it is the
   reason the column should not be casually exported into a spreadsheet or a
   third-party annotation tool without a decision.
3. **Training use belongs in the privacy policy before it starts.** Storing for
   analysis and training on it are different commitments to a user; the second
   wants a line in the policy. Worth doing before the first public query, not
   retroactively.

Suggested, not required: a `retention_note` or a periodic review, so "we keep
query text indefinitely" is a decision someone made rather than a default that
accumulated.

## The store seam

Follows the existing `ActionStore` idiom — one interface, a local
implementation now, a Supabase implementation later, chosen in `services.ts` by
credential presence. See `packages/server/src/data/QueryStore.ts`.

The seam deliberately exposes **no method that reads app data for scoring**.
There is no `getPriorVerdicts`, no `getSimilarQueries`, no aggregate. The only
reads are by `id`, for rendering a shared result back to the person who made it.
If a future feature wants "what do other people ask about this senator", that is
a product analytics question and belongs on a separate seam with its own review
— not a convenience method here.

## Deployment shape this implies

- **`packages/web`** → static build. Reads no env, holds no secret; the one
  build-time variable is `SERVER_ORIGIN` for the dev proxy.
- **`packages/server`** → Node service, holds every secret, is the only thing
  that talks to Anthropic, OpenAI, Pinecone and Supabase.
